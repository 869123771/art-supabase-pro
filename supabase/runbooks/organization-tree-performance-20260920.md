# 组织树读取优化记录（2026-09-20）

目标项目：`ckbftoopuyophiebamwy`。本次只改变现有只读函数 `public.get_organization_list_secure(text, uuid, text, text, uuid)` 的内部查询，以及前端组织选择树的数据来源；未改变函数签名、返回列、授权、表结构或 RLS。

## 原因与实现

- 原函数对每个组织分别执行成员数、角色数、菜单数的相关子查询。`pg_stat_statements` 中两个常见调用形态分别约 762 次 / 平均 254 ms、654 次 / 平均 292 ms。
- 函数现在先确定可见组织，再按组织批量聚合三项计数。仍以调用者权限执行，读取同样的 `mdm_organization`、`sys_user`、`sys_role`、`sys_role_menu`；租户范围继续由现有 RLS 和请求上下文约束。
- 仅需组织身份与层级的 HR、MDM、SMIS 选择树改用 `mdm_organization` 的窄字段投影，组织管理页保留带计数的函数。用户组织筛选树的成员计数排除已删除账号，与用户列表一致。

## 回退资料

修改前的完整函数定义保存在本工作区忽略目录 `.artifacts/get_organization_list_secure.before.backup.txt`，与修改前数据库定义逐字核对一致。全量 schema 备份因本机 Docker 未运行而无法生成；本次只替换此函数，未修改业务数据。需要回退时，先检查当前函数定义及依赖，在事务中执行该备份定义并核对返回结果，再提交。不要将备份当作迁移文件发布。

## 验证

- 在一个回滚事务内替换函数并比较完整返回值：普通用户、普通用户伪造其他租户请求头、平台全部租户、平台选定租户四种上下文均与旧版逐项相同，分别返回 8、8、39、8 条组织。回滚后确认旧函数定义仍在，再正式直接执行替换。
- 正式替换后确认数据库定义与审阅版本一致；仍为 `STABLE`、`SECURITY INVOKER`，`authenticated` 执行授权不变，启用组织查询返回 39 条。
- 新的直读路径已核对：`authenticated` 对 `mdm_organization` 和 `sys_tenant` 均有 `SELECT` 授权；不存在的用户 ID 在现有 RLS 下返回 0 行而不报错；组织到租户的 `sys_organization_tenant_id_fkey` 关系存在。
- 同一查询的 `EXPLAIN (ANALYZE, BUFFERS)`：替换前约 141 ms，替换后暖缓存约 24 ms。执行计划耗时受缓存和负载影响，不应当作固定用户侧延迟。
- 在一个普通用户的 RLS 上下文中复测，旧版约 507 ms、新版约 503 ms；该上下文主要耗时仍在权限判断中，不能宣称普通用户获得上述 141 → 24 ms 的加速。后续若处理 RLS 性能，应另行审计权限函数和租户四场景，不以绕过 RLS 换速度。
- 修改后运行 Supabase 安全与性能顾问；均未报告与该函数相关的新发现。其他全库告警不在本次范围内。
