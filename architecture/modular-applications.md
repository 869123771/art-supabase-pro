# 独立业务应用架构

## 仓库边界

| 应用代码 | 仓库 | 负责范围 |
| --- | --- | --- |
| `platform` | `art-supabase-pro` | Auth、租户、用户、组织、菜单、角色权限、数据中心与共享数据库契约 |
| `finance` | `art-supabase-finance` | Finance 独立应用预留边界 |
| `fms` | `art-supabase-fms` | FMS 财务管理 |
| `hr` | `art-supabase-hr` | HR 人力资源 |
| `smis` | `art-supabase-smis` | SMIS 安全生产 |
| `vms` | `art-supabase-vms` | VMS 车辆管理 |

当前采用“多业务源码仓 + 单一平台宿主”模式。平台宿主聚合当前用户可访问应用的菜单；平台超级用户可以进入全部已启用应用，普通租户用户只能进入其角色拥有菜单的应用。`VITE_APP_CODE` 和单应用菜单查询能力保留为将来拆分独立运行壳的兼容契约。

## 平台聚合与统一认证

- `art-supabase-pro` 是唯一公共运行壳，拥有登录、注册、找回密码、租户、用户、菜单和权限。
- 业务仓不复制 `views/auth`，只消费平台已经建立的 Supabase 会话；未登录时回到平台登录页。
- 主仓通过 Git submodule 固定提交引用业务仓，平台启动时直接装载被引用版本的业务页面。业务源码仍只在业务仓维护，主仓不再复制一份。
- 子仓名称已经表达领域，内部目录保持扁平，例如 VMS 使用 `src/views/archive-manage` 与 `src/api/index.ts`。数据库菜单继续保存 `/vms/...` 稳定前缀，由平台组件加载器映射到子仓视图根目录。
- 当前生产环境只部署 `art-supabase-pro` 宿主产物；VMS 等业务仓作为固定版本的源码模块进入该产物，不单独复制公共运行壳。
- 登录回跳只传递同源页面 URL，不在 URL、日志或菜单配置中传递 access token / refresh token。不同域名部署必须增加服务端一次性授权码 SSO，不能直接复制浏览器令牌。

## 数据交互原则

1. 业务表仍位于同一 Supabase 项目，登录态、租户上下文和事务边界保持一致。
2. 表的写入只归领域所有者。其他模块不得直接写该领域表，也不得导入该模块的前端 API 实现。
3. 跨域读取使用用途明确的 RPC / Read Model。契约在数据库边界校验 `auth.uid()`、租户、业务菜单权限与字段可见性。
4. Realtime 仅用于“数据已变化”的失效通知；收到通知后重新调用只读契约，不把事件负载当作授权后的业务数据。

VMS 实验包含两类真实契约：

- VMS 通过 TMS 的安全引用数据 RPC 获取承运商、司机；TMS 仍拥有源数据和字段脱敏规则。
- `vms_list_hr_employee_options_secure` 向 VMS 提供 HR 在职员工的最小只读投影，不返回身份证、联系方式等非必要敏感字段。

## 部署与回滚

- 每个业务仓独立版本化并执行领域边界检查、单元测试；主仓固定业务仓提交后统一执行类型检查、生产构建和发布。
- 当前 `sys_application.base_url` 指向平台宿主地址，模块切换通过各自的稳定路由前缀完成。独立域名只有在服务端 SSO 契约完成后才能启用。
- 前端发布与数据库契约保持向后兼容：先发布新增契约，再发布消费者；回滚时先回滚消费者，确认无调用后再移除契约。
- 基座只通过 Git submodule 提交指针和公开入口装载业务源码，不复制或直接修改业务实现。业务仓允许依赖稳定的平台公共契约，但不能通过相对路径或源码别名反向引用其他业务仓。

## 子工程命令

| 命令                   | 用途                                                               |
| ---------------------- | ------------------------------------------------------------------ |
| `pnpm modules:pull`    | 初始化子模块，并拉取主仓 gitlink 锁定的版本                        |
| `pnpm modules:update`  | 更新到各子工程远端配置分支的最新提交；执行后需要检查并提交 gitlink |
| `pnpm modules:install` | 按各子工程自己的 lockfile 安装全部依赖                             |
| `pnpm modules:build`   | 依次构建全部子工程                                                 |
| `pnpm modules:setup`   | 一次完成锁定版本拉取、依赖安装和全部构建                           |
