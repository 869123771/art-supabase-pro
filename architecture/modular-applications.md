# 独立业务应用架构

## 架构结论

平台与业务应用采用“独立仓库、独立运行、独立构建、独立部署，共享平台契约；平台可选聚合本地业务源码”的模式。`art-supabase-pro` 会聚合当前用户角色有权访问的应用菜单；本地已经初始化的业务子仓页面可直接装载到平台内容区，未初始化的业务子仓不再阻断主仓安装、启动、检查或构建，对应授权菜单进入后显示“子模块未装载”提示。

## 仓库与所有权

| 应用代码   | 仓库                | 代码与发布所有权                                             |
| ---------- | ------------------- | ------------------------------------------------------------ |
| `platform` | `art-supabase-pro`  | Auth、租户、用户、菜单、角色权限、数据中心与共享前端运行契约 |
| `fms`      | `art-supabase-fms`  | FMS 财务管理应用                                             |
| `hr`       | `art-supabase-hr`   | HR 人力资源应用                                              |
| `mdm`      | `art-supabase-mdm`  | MDM 主数据治理、统一目录与跨域只读契约                       |
| `mes`      | `art-supabase-mes`  | MES 制造执行应用                                             |
| `smis`     | `art-supabase-smis` | SMIS 安全生产应用                                            |
| `vms`      | `art-supabase-vms`  | VMS 车辆管理应用                                             |
| `tms`      | `art-supabase-tms`  | TMS 智慧运输应用                                             |
| `wms`      | `art-supabase-wms`  | WMS 仓储管理应用                                             |
| `docs`     | `art-supabase-doc`  | 产品、开发与运维文档站                                       |

每个业务仓拥有自己的 `package.json`、lockfile、`src/main.ts`、页面、领域 API、质量门禁和部署产物。主仓提供可版本化的平台公共契约，但不反向导入业务仓源码。

## 运行时边界

1. 每个部署通过 `VITE_APP_CODE` 声明自己的应用身份。
2. 每个应用只注册自己的页面，并只请求自己的菜单与按钮权限。
3. 平台应用聚合当前用户有权访问的全部应用菜单；没有初始化任何 submodule 时也必须正常启动和构建。
4. 业务应用通过 `registerApplicationViewModules` 把本仓页面接入共享路由加载器。该 API 是独立应用壳契约，不代表平台宿主业务源码。
5. 平台宿主只装载工作区中实际存在的业务源码；缺失子仓时保留授权菜单，并在内容区给出可恢复的缺失模块状态。
6. 应用切换器调用 `get_accessible_applications` 获取当前用户可访问的应用及 `base_url`，支持跳转到独立部署的业务应用。

## 认证与数据契约

- 登录、租户与 RBAC 仍由平台 Supabase 项目统一管理。
- 同源不同路径部署可以复用同一浏览器会话。不同域名部署必须使用服务端一次性授权码 SSO，不能在 URL、日志或菜单配置中传递 access token / refresh token。
- 业务表写入归领域所有者。其他应用不得直接写该领域表，也不得导入该应用的前端 API 实现。
- 跨域读取使用用途明确的 RPC / Read Model，并在数据库边界校验用户、租户、菜单权限和字段可见性。
- Realtime 只发送失效通知；消费者收到通知后重新读取授权后的契约数据。

## 构建、发布与回滚

- 每个仓库可以独立执行安装、类型检查、代码规范、测试、构建和发布。
- 主仓标准 CI 不要求初始化业务 submodule；需要发布“平台内嵌全部业务页面”的聚合产物时，再通过可选多仓命令锁定并构建对应子仓。
- 共享平台契约通过明确版本升级。先发布向后兼容的平台/数据库契约，再升级消费者。
- 回滚时先回滚消费者；确认没有调用后，再移除废弃契约。
- `sys_application.base_url` 是跨应用导航的发布地址来源。修改部署地址不需要重新打包平台源码。

## 可选多仓工作区

`.gitmodules` 可以保留，用于在 WebStorm 等 IDE 中同时打开多个独立 Git 根目录或执行人工集成验证。这些命令不会成为主仓日常生命周期的一部分：

| 命令                   | 用途                                               |
| ---------------------- | -------------------------------------------------- |
| `pnpm modules:status`  | 可选：查看全部子仓初始化和版本状态                 |
| `pnpm modules:pull`    | 可选：初始化并拉取锁定版本，传输中断时自动逐仓重试 |
| `pnpm modules:update`  | 可选：逐仓更新远端配置分支并检查 gitlink 变化      |
| `pnpm modules:install` | 可选：自动初始化并按各仓 lockfile 安装依赖         |
| `pnpm modules:check`   | 可选：自动初始化并逐仓执行质量门禁                 |
| `pnpm modules:build`   | 可选：自动修复不完整依赖并逐仓构建                 |
| `pnpm modules:setup`   | 可选：一次完成拉取、安装和构建                     |
| `pnpm build:all`       | 先构建全部子仓，再构建主仓；各仓产物互不合并       |

以上 `modules:*` 命令默认作用全部子仓；末尾可传一个或多个简称，只作用指定子仓，例如 `pnpm modules:install -- vms fms`。统一安装会从本地主仓 Git 历史按每个子仓锁定的提交生成依赖包，避免重复下载 Gitee 主仓归档；子仓独立安装和部署时仍使用自身锁文件记录的远端版本。

完整独立发布使用 `pnpm build:all`。它复用逐仓构建流程，构建前会按仓检查直接依赖和平台类型入口，只自动修复依赖不完整的子仓；随后把每个子仓构建到该仓自己的发布目录，再把主仓构建到根目录 `docs`，不会把各仓产物集中复制到同一个目录。业务应用子仓的发布目录均为各自的 `docs`；文档站遵循 VitePress 约定，发布目录为其 `docs/.vitepress/dist`。

主仓的标准命令始终只作用于主仓：

```powershell
pnpm install
pnpm dev
pnpm check
pnpm build
```
