# MDM 高可用、灾备与恢复运行手册

## 1. 适用范围与责任

本手册适用于 Supabase 项目 `ckbftoopuyophiebamwy`（`ap-south-1`）中的 MDM 目录、治理控制面、审批、黄金记录、来源映射和 Outbox 交付数据。

| 角色 | 主要责任 |
| --- | --- |
| MDM 数据负责人 | 确认主档业务优先级、质量规则、恢复后的业务抽样结果 |
| 平台超级管理员 | 批准发布、死信重放、灾备切换和恢复完成 |
| 数据库值班人员 | 监控数据库、执行 PITR/逻辑恢复、保留证据 |
| 来源适配器负责人 | 保证消费幂等、处理重试/死信、完成恢复后的追平 |
| 安全与审计 | 复核访问、恢复、越权和不可变审计证据 |

## 2. 服务目标

以下目标是上线门禁，不是云厂商默认承诺。每季度用演练证据重新确认。

| 能力 | 目标 | 计算口径 |
| --- | --- | --- |
| 治理查询可用性 | 月度 ≥ 99.95% | 有权限用户成功加载治理概览和列表的分钟数 |
| 治理写入可用性 | 月度 ≥ 99.90% | 有权限且合法的 RPC 成功完成的请求比例 |
| p95 查询延迟 | ≤ 800 ms | 治理概览、问题/变更/匹配/投递列表 |
| p95 写入延迟 | ≤ 1.5 s | 质量状态、变更审批、匹配评审、死信重放 |
| Outbox 正常交付 | 99% ≤ 5 min，99.9% ≤ 30 min | 从 `occurred_at` 到 `delivered_at` |
| 同区域 RPO | ≤ 5 min | 最近可恢复点与事故时间的差值 |
| 同区域 RTO | ≤ 60 min | 宣布事故到核心 MDM 恢复可用 |
| 区域级灾难 RPO | ≤ 24 h | 最近完成且异地保存的全量备份 |
| 区域级灾难 RTO | ≤ 4 h | 新项目恢复、密钥轮换、适配器切换和验收 |

若当前套餐没有 PITR，正式上线不得宣称满足 5 分钟 RPO；必须升级支持 PITR 的数据库方案，或把目标降级并由业务负责人书面接受。Supabase 的备份、PITR 与只读副本能力以官方文档为准：

- <https://supabase.com/docs/guides/platform/backups>
- <https://supabase.com/docs/guides/platform/read-replicas>

`supabase backups list --project-ref ckbftoopuyophiebamwy` 返回：项目健康且 `walg_enabled=true`，但 `pitr_enabled=false`，可列出的平台物理备份为空。因此当前项目**不能证明满足 5 分钟 RPO**。仓库逻辑全量备份用于补齐可恢复副本，但不能替代 PITR；启用 PITR/只读副本如涉及套餐或费用，必须由项目所有者在 Supabase 控制台批准后执行。

## 3. 架构与降级原则

1. **单一写入权威**：来源系统主档仍为权威写模型。治理端不直接更新来源主档；已批准变更写入 Outbox，由来源适配器执行。
2. **按消费者隔离**：每个消费者拥有独立 delivery、尝试次数、可见性锁和死信。一个下游故障不得阻塞其他下游。
3. **至少一次交付**：消费者必须以 `event_id` 作为幂等键。重复收到同一事件只能返回既有结果，不得重复执行业务副作用。
4. **读写降级**：写路径异常时，保留租户内只读目录与历史查询；禁用新变更、合并、发布和重放。读副本只承接允许最终一致的目录/报表查询，不承接审批后立即读和任何写入。
5. **租户隔离不降级**：任何故障模式都不得关闭 RLS、扩大匿名权限或绕过复合租户外键。

## 4. 监控与告警

### 4.1 必须采集

- Supabase 项目健康、数据库 CPU/内存/连接数、磁盘和慢查询。
- `mdm_quality_issue`：开放量、逾期量、按严重级别和责任人分布。
- `mdm_change_request`：待审核量、到期未发布量、状态停留时间。
- `mdm_match_candidate`：待评审量与最老候选年龄。
- `mdm_outbox_delivery`：pending/retry/dead-letter 数量、最老未送达年龄、尝试次数。
- RLS 拒绝、RPC 权限拒绝、登录/令牌异常与平台超管写入审计。

### 4.2 告警门槛

| 级别 | 条件 | 首次响应 | 动作 |
| --- | --- | --- | --- |
| SEV-1 | 数据库不可用、确认跨租户泄漏、不可逆错误发布、恢复失败 | 5 min | 冻结治理写入，召集平台/数据库/安全负责人 |
| SEV-2 | 死信 > 0 且持续 10 min、关键质量问题逾期、Outbox 最老未送达 > 30 min | 15 min | 隔离故障消费者，保留其他交付，建立事件记录 |
| SEV-3 | p95 超目标 15 min、重试积压、规则扫描失败 | 30 min | 限流、扩容或暂停批处理，安排根因分析 |

## 5. 标准发布

1. 确认 `supabase/migrations` 的本地/远端历史完全对齐。
2. 运行 `supabase/backup-supabase.ps1`，确认备份目录包含 `manifest.json`、数据库三份 SQL、迁移历史、Storage/Functions 元数据。
3. 在远端事务中执行候选迁移并回滚，证明 SQL 能作用于真实结构和现有数据。
4. 用本地 `supabase db reset` 从 baseline 重建并执行全部 SQL 测试。
5. 低流量窗口执行 `supabase db push --dry-run`，人工复核仅包含已批准迁移。
6. 持久发布后检查约束、RLS、菜单权限、治理 RPC、Outbox 和性能顾问。
7. 观察至少 30 分钟；失败时停止新写入，按第 7 节回退，不删除审计/Outbox 证据。

## 6. 备份策略

- 平台备份/PITR：启用并每日检查最近可恢复点；告警窗口不得超过目标 RPO。
- 每日逻辑备份：在低峰执行 `supabase/backup-supabase.ps1`，加密后复制到与生产不同故障域的对象存储。
- 发布前备份：所有数据库变更前必须生成一次完整 manifest。
- 保留期：每日 35 天、月末 13 个月、年度 7 年；如适用法规要求更长，以法规为准。
- 密钥：数据库密码、JWT/服务角色密钥和 Edge Function secret 不进入备份仓库；恢复后从密钥系统重新注入并轮换。
- 校验：备份完成即校验文件存在、非空、SHA-256 清单和 manifest；仅“命令成功”不足以证明可恢复。

## 7. 恢复流程

### 7.1 误操作或数据损坏（PITR）

1. 宣布事故并冻结 MDM 治理写入、自动发布、匹配合并和死信重放。
2. 记录事故时间、最后确认正确时间、受影响租户/表/事件 ID。
3. 优先恢复到隔离的新项目，不覆盖原项目。
4. 选择“最后确认正确时间”之后最接近且早于破坏动作的恢复点。
5. 对照第 8 节验证；安全和业务负责人签字后才切换连接。
6. 恢复窗口后产生但未包含的数据，从来源系统与 Outbox 审计进行受控追平，禁止手工无审计覆盖。

### 7.2 区域或项目不可恢复（逻辑备份）

1. 新建空 Supabase 项目，区域由灾备负责人按故障范围选择。
2. 运行：

   ```powershell
   .\supabase\restore-supabase.ps1 `
     -BackupPath '<validated-backup-directory>' `
     -TargetProjectRef '<new-project-ref>'
   ```

3. 重新注入 Edge Function secrets，轮换数据库、JWT 和服务角色密钥。
4. 部署适配器，并用新的 `event_id` 幂等库或恢复后的消费表继续交付。
5. 完成第 8 节全部验证后切换 DNS/配置；保留旧项目只读直至复盘结束。

## 8. 恢复验收

恢复只有同时满足以下条件才算完成：

- 所有 public MDM 表启用 RLS，匿名角色没有表权限。
- 19 条历史 MDM 关系均为 tenant-qualified 复合外键，跨租户违规数为 0。
- 质量问题和变更事件表不可 UPDATE/DELETE。
- 四眼规则有效：申请人不能审核自己的申请，整改人不能复核自己。
- 黄金记录与 crosswalk 数量、哈希抽样、来源标识匹配业务基准。
- Outbox 每个消费者的 pending/retry/dead-letter 数量与事故记录一致；随机重放一条测试事件只产生一次下游副作用。
- 关键主档表按租户的 `count(*)`、`min(create_time)`、`max(update_time)` 与备份 manifest/事故基线一致。
- 前端桌面、移动端、暗色与盒式布局没有溢出，治理只读与写权限表现正确。

## 9. 演练与证据

- 每月：在隔离环境恢复最近逻辑备份，验证结构、RLS、约束和抽样记录。
- 每季度：完整 PITR 或新项目恢复演练，记录实际 RPO/RTO、执行人、开始/结束时间、失败点和改进项。
- 每半年：注入消费者超时、重复消费、数据库连接耗尽和单消费者死信，验证隔离、退避和重放。
- 每年：区域级切换演练，包括密钥轮换、适配器重连、业务验收和回切。

演练证据至少保留：命令版本、备份 manifest、哈希清单、SQL 验证结果、关键页面截图、告警时间线、批准人和复盘链接。未完成恢复演练的备份只能称为“已生成”，不能称为“可恢复”。
